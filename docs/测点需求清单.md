# 全站总功率预测测点需求清单

## 1. 使用范围

本清单对应生产部署包当前活动模型，适用于十个场站全站总功率预测服务。

- 采样间隔：15 分钟
- 每次请求：最近一天 96 个连续时间点
- 功率测点：29 个
- 温湿度输入配置项：23 个（温度 12 个、湿度 11 个；其中湿度有 1 个编码被两个场站共用）
- 功率单位：MW

每个时间点先将十个场站的全部功率测点直接求和，得到 total_power，再送入全站总功率预测模型。不是对每个测点单独预测后再求和。

## 2. 测点处理规则

| 测点类型 | 模型使用方式 | 缺失或非数字 | 数值 0 |
|---|---|---|---|
| 功率 | 参与十场站总功率求和 | 使用缓存中该测点上一个真实值 | 保留为有效值 |
| 温度 | 构造模型温度特征 | 使用缓存中该测点上一个真实值 | 保留为有效值 |
| 湿度 | 构造模型湿度特征 | 使用缓存中该测点上一个真实值 | 保留为有效值 |

首次缓存中某测点没有任何真实值时，不能随机生成、固定填充或擅自按零处理；该测点无法完成真实值补齐时，接口返回错误。服务不插值、不做低负荷修复、不改写异常值。

深圳钰湖的两个华氏温度测点在模型输入前由程序转换为摄氏度；其他测点按程序当前配置处理。

## 3. 按场站列出的输入字段

下面的表格按照原始 CSV 的组织方式列出。每个场站单独列出自己的字段：第一列是原始 CSV 列名，也是 JSON 中实际使用的测点字段名；第二列是 JSON 字段路径模板，说明这个字段位于 `load_points` 还是 `weather_points`。每个字段的值类型为 JSON number，单位必须与表中一致。

接口字段的完整层级是：

```text
data[].ts
data[].stations["场站名称"].load_points["功率测点编码"]
data[].stations["场站名称"].weather_points["温湿度测点编码"]
```

例如，高安屯热电的功率字段完整写法是：

```json
{
  "data": [
    {
      "ts": "2025-12-31 23:45:00",
      "stations": {
        "高安屯热电": {
          "load_points": {
            "GARD_11MBY0100000BJ01XQ01": 165.69
          },
          "weather_points": {
            "GARD_11MBL3100000BT01XQ01": -4.43
          }
        }
      }
    }
  ]
}
```

表中 `[...]` 只是表示“该行第一列的测点编码”，实际请求中必须使用完整编码，不能把省略号作为字段名传入。

### 3.1 请求固定字段

| JSON 层级 | 字段 | 类型 | 是否必填 | 说明 |
|---|---|---|---|---|
| 请求根对象 | `batchTime` | string | 否 | 本批次标识；未提供时服务使用最后一个 `ts` 生成 |
| 请求根对象 | `intervalMinutes` | integer | 是 | 必须为 `15` |
| 请求根对象 | `historyDays` | integer | 是 | 必须为 `1`，表示本次提交最近一天 |
| 请求根对象 | `data` | array | 是 | 必须包含 96 个连续的 15 分钟时间点 |
| `data[]` | `ts` | string | 是 | 当前时间点，格式如 `2025-12-31 23:45:00` |
| `data[]` | `stations` | object | 是 | 十个场站的测点对象；场站名必须使用第 3.2 至 3.11 节的名称 |
| `stations[场站名称]` | `load_points` | object | 是 | 该场站的功率测点，key 使用原始 CSV 列名 |
| `stations[场站名称]` | `weather_points` | object | 是 | 该场站的温度、湿度测点，key 使用原始 CSV 列名 |

`data[]` 是接口实际传输的时间点数组；表中的 `load_points` 和 `weather_points` 不是额外模型变量，而是原始测点在 JSON 中的分组对象。每个测点的完整字段路径由“场站名称 + 分组对象 + 测点编码”组成，例如：

```text
data[].stations["高安屯热电"].load_points["GARD_11MBY0100000BJ01XQ01"]
```

## 4. 这些输入是否都是模型需要的

结论：**当前接口清单中的所有字段都需要保留，但它们不是 52 个直接并列送入神经网络的输入列。**它们是模型的原始输入测点，程序会先聚合和派生特征。

### 4.1 原始测点到模型变量

| 输入层级 | 数量 | 程序处理 | 是否由调用方传入 |
|---|---:|---|---|
| 功率测点 | 29 个 | 同一场站功率点求和为各站 `*_total_power`，再将十站站点总功率求和为 `total_power` | 是 |
| 温度测点 | 12 个 | 同一场站温度取均值，再将十站温度汇总为全局 `temperature`；深圳钰湖两个点先由华氏度转摄氏度 | 是 |
| 湿度测点配置项 | 11 个 | 同一场站湿度取均值，再将十站湿度汇总为全局 `humidity` | 是 |
| 去重后的湿度编码 | 10 个 | 深圳钰湖和钰海电力共用 `YHDL_11MBL1000000BM01XQ01`，但当前 JSON 仍按两个场站字段分别提供 | 是，按两个场站位置提供 |
| 场站功率有效性 | 10 个站点状态 + 3 个统计量 | 由本次功率测点是否完整上送、缓存补齐情况自动生成 | 否 |
| 功率状态特征 | 每站 2 个 | 由各站 `*_total_power` 的历史状态中心和状态编号自动生成 | 否 |
| 时间特征 | 10 个历史特征 | 由 `ts` 自动生成小时、星期、月份、年内日期、周末和采暖季等特征 | 否 |

因此，接口调用方不需要计算或传输 `total_power`、各站 `*_total_power`、`temperature`、`humidity`、有效性字段、状态字段和时间特征；只传第 3 节列出的原始测点字段即可。

### 4.2 当前离线模型真正使用的输入

当前活动模型的历史输入共有 **56 个派生特征**，组成如下：

```text
1 个全站 total_power
10 个场站 *_total_power
2 个全局 temperature / humidity
3 个有效性统计量
10 个场站 station_valid
20 个场站功率状态和状态中心
10 个时间特征
= 56 个历史特征
```

模型链的输入方式也不完全相同：

- `NHITS` 和 `PatchTST` 使用最近 **288 点（3 天）**的 `total_power` 序列，输入是时间和总功率两列。
- `StationAttentionHF` 使用最近 **672 点（7 天）**的 56 个历史特征，并使用未来 96 点自动生成的 32 个时间/状态特征。
- 最终输出由上述分支经过融合和 TrendDetail 后得到未来 96 点的全站总功率预测。

所以，**29 个功率测点和 23 个温湿度配置项全部属于当前模型输入链路，不能删除；但它们先被程序聚合成 56 个历史模型特征，调用方也不需要自己生成这 56 个特征。**

## 5. 传输要求

- 正式请求使用第 3 节的场站名称、`load_points` / `weather_points` 字段和测点编码。
- 每个请求的 `data` 必须包含最近一天 96 个连续时间点，间隔为 15 分钟。
- 生产环境建议每个时间点都上送十个场站的全部字段；某个字段缺失时，服务只能使用缓存中该测点上一真实值补齐。
- 首次缓存还没有历史时，本批次开头的缺失值可以使用该测点在本批次首次出现的真实值初始化；如果整个可用历史中从未出现真实值，接口返回错误。
- 真实数值 `0` 必须传数字 `0`，不能当作空值或缺失值。
- 不要增加未在清单中的场站或测点；服务会拒绝未知字段。
